# Easy TRV 0.5 — Room state, silent contacts, areas, hidden thermostat entities

Derived from the owner's decisions of 2026-10-15 (click answers in the working session) and from the Phase 2 design in `2026-10-14-easy-trv-phase2-design.md`, which stays valid wherever this document is silent.

Trigger: in the bedroom an open balcony door did not switch the heating off. The contact was `unavailable`. Easy TRV handled that as designed (owner ruling I3: a silent contact keeps its last state, one never seen counts as closed), but nothing told the person. 0.5 makes the room's situation visible and adds two setup conveniences the owner asked for in the same round.

| Part | Scope |
|---|---|
| **A** | a visible state sensor per room: one state, all reasons, an event on change |
| **B** | a silent window contact becomes visible: in the state sensor at once, as a Repairs issue after 10 minutes |
| **C** | the Easy TRV entities of a room created from an area sit in that area |
| **D** | opt-in: hide the thermostat entities Easy TRV controls |

Release: `0.5.0`.

## A. Room state sensor

### A.1 Entity

- One `sensor` per room on the room device, `unique_id` `<subentry_id>_state`, suggested entity id `sensor.<slug(room title)>_heating_state`, `translation_key` `room_state`, device class `enum`, **no entity category** (it belongs on dashboards and in automations; the existing status sensor stays under diagnostics).
- Icons per state in `icons.json`.
- Names (owner, 2026-10-15: the status must be easy to find by its name). Home Assistant 2026.10 shows the entity part of a name on its own in lists and strips a leading device name, so the entity part has to say what it is: this sensor is „Heizungszustand“ / „Heating state“, and the existing status sensor is renamed from „Status“ to „Heizungsstatus“ / „Heating status“. Full names: „Heizung Wohnzimmer Heizungszustand“, „Heizung Wohnzimmer Heizungsstatus“. Entity ids do not change.

### A.2 States and priority

The state is the first of these conditions that holds. The order is also the order of `options`.

| Value | de | en | Holds when |
|---|---|---|---|
| `fault` | Störung | Fault | a thermostat's health is `error` (the room status is `error`) |
| `off_manual` | Aus (manuell) | Off (manual) | the room's operating mode is `off` |
| `off_window` | Aus: Fenster/Tür offen | Off: window/door open | the window hold is active |
| `off_outdoor` | Aus: Außentemperatur | Off: outdoor temperature | the outdoor hold is active |
| `off_away` | Aus: Abwesenheit | Off: away | never yet (placeholder for the presence feature) |
| `window_pending` | Fenster offen, schaltet gleich ab | Window open, switching off soon | a contact is open and the open delay is running |
| `emergency` | Notbetrieb | Emergency mode | the room has temperature sensors but the source is not external, or a thermostat signalled its fail-safe within the refresh interval (the two sensor conditions that make the status `degraded`) |
| `restricted` | Eingeschränkt | Restricted | a thermostat is unavailable or unsupported, a thermostat carries the note `schedule` or `window_phase`, or a window contact is silent (B) |
| `boost` | Handbetrieb (Boost) | Manual (boost) | never yet (placeholder for boost) |
| `frost` | Frostschutz | Frost protection | the operating mode is `frost` |
| `heating` | Heizbetrieb | Heating | the operating mode is `heat` |

`off_manual` comes before the holds on purpose: while the person switched the room off, the window does not decide anything, and the room stays off after it closes.

### A.3 Attributes

- `reasons`: every condition of A.2 that holds, in priority order. The first element is the state. The operating mode (`off_manual`, `frost` or `heating`) is always in the list.
- `since`: ISO timestamp of the last change of the state. After a restart it is the time of the first evaluation.
- `window_off_at`: ISO timestamp at which the running open delay switches the room off; `null` otherwise.
- `thermostats`: map of thermostat climate entity → why it deviates, only for those that do. Values: `error`, `unavailable`, `unsupported`, `schedule`, `window_phase`. A thermostat with more than one reason shows the first of that order.
- `silent_contacts`: the window contacts that currently say nothing (`unavailable`, `unknown` or missing), sorted.

Attribute names are translated in `entity.sensor.room_state.state_attributes`, attribute values of `thermostats` are not.

### A.4 Event

`easy_trv_state_changed` with `room` (the room's title), `state`, `previous`, `reasons`. Fired when the state changes from one value to another, not for the first evaluation after a start.

### A.5 Where the logic lives

- `core/room_state.py`: a pure function from a small fact record to `(state, reasons)`, plus the `HeatingState` enum. No Home Assistant imports, full test matrix.
- The controller builds the facts from the core state and the hold inputs, keeps `since` and the previous state, fires the event, and publishes through its update listeners.
- The window delay becomes visible: arming the delay, firing it and cancelling it each call the controller's `changed` callback, so `window_pending` and `window_off_at` appear and disappear without a logic event.

## B. Silent window contacts

- **Behaviour stays.** A silent contact keeps its last state; one never seen since the start counts as closed (owner ruling I3). A contact that falls silent does not change the heating: one last seen closed or never seen does not switch it off, one last seen open keeps it off until it reports again.
- **Visible at once.** The state sensor shows `restricted` with the contact in `silent_contacts`; `in_sync` stays `false` as before.
- **Repairs issue after 10 minutes.** When a room's set of silent contacts becomes non-empty, a timer of 10 minutes (constant `CONTACT_SILENT_ISSUE_MINUTES = 10`, not a setting: it rides out ZHA's start-up) starts. If contacts are still silent when it fires, the issue `window_contact_unavailable_<room_id>` (severity warning, not fixable) is raised with the placeholders `room` and `contacts` (friendly names, else entity ids, comma-separated, sorted). While raised, a change of the silent set re-raises it with the new list. When the set becomes empty the timer is cancelled and the issue removed.
- Text (de): title „Fensterkontakt im Raum {room} nicht erreichbar“; body: „Seit mindestens 10 Minuten meldet im Raum {room} ein Fensterkontakt keinen Zustand. Gerade ohne Meldung: {contacts}. Easy TRV behandelt einen solchen Kontakt so, wie er zuletzt war: Ein zuletzt geschlossener oder nie gesehener Kontakt gilt als geschlossen, ein Öffnen schaltet die Heizung dann nicht ab. Ein zuletzt offener Kontakt hält die Heizung aus, bis er sich wieder meldet. Prüfe Batterie und Funkverbindung.“ English to match. (Reworded after the Task 2 review: the list can hold several contacts, and one that joined later has been silent for less than 10 minutes.)
- The room's controller removes the issue when it starts and stops (like the other window issues); `clear_window_issues_except` also covers it for rooms that are gone.

## C. Areas

Owner's words: the entities Easy TRV creates go into the area automatically when the room was set up from an area.

- A room keeps its area in `area_id` (existing key). Rooms from an area have it since 0.2; the custom-room step and the reconfigure step get an optional area field, so every room can have one and it can be changed.
- **At every setup**, after the platforms are set up: a room whose area exists and whose room device has no area gets its device put into that area. This fixes the existing devices, which were created before or without the area.
- **When the reconfigure step saves a different area** (not empty), the flow moves the room device into the new area before it saves. Emptying the field leaves the device where it is.
- A device area the person set by hand stays, as long as the room's area is not changed. Easy TRV never sets the area of an entity; entities follow their device unless the person gave one its own area.
- `suggested_area` stays on the device info: it still places a newly created device.

## D. Hiding the thermostat entities Easy TRV controls

Home Assistant's own pattern: the group helper's "hide members" and `switch_as_x` hide the entities they take over with `hidden_by = integration` and show them again when they let go.

- **Setting** `hide_thermostat_entities`, values `on` / `off`, default `off`, global (options section "thermostat") with a room override (room settings step, after the frost temperature), following the pattern of `window_warn_colder`.
- **What is hidden, per thermostat of a room with the setting on:** its climate entity, plus the entities on the same device (entity registry, platform `zha`) whose `domain` and `translation_key` match a capability of the room's profile that names one. Nothing else: child lock, boost and timer buttons, valve degrees, battery and sensors stay as they are (owner: "only what Easy TRV controls").
- **Profile:** a capability may name its entity: `entity: { domain: <str>, translation_key: <str> }` (both required when present). The Sonoff TRVZB profile names six:

  | Capability | domain | translation_key |
  |---|---|---|
  | `external_temperature` | `number` | `external_temperature_sensor_value` |
  | `source_select` | `switch` | `external_temperature_sensor` |
  | `window_detection_flag` | `switch` | `open_window` |
  | `hysteresis` | `number` | `temperature_control_accuracy` |
  | `adaptive_mode` | `switch` | `adaptive_mode` |
  | `frost_protection` | `number` | `frost_protection_temperature` |

  `setpoint` and `hvac_mode` belong to the climate entity, which is hidden anyway.
- **Marker:** an entity Easy TRV hid carries the entity-registry options `{"hidden": true}` under the domain `easy_trv`.
- **Reconcile at every setup**, after the rooms are built:
  - an entity that should be hidden, has no marker and is not hidden → `hidden_by = integration`, marker set;
  - an entity that should be hidden and has the marker → left alone, also when the person showed it again (their choice stays);
  - an entity with the marker that should no longer be hidden (setting off, thermostat or room removed) → shown again if `hidden_by` is still `integration`, marker removed.
  - The thermostats of a room that cannot be set up keep their entities as they are.
- **Entry removed** (`async_remove_entry`): every marked entity is shown again if `hidden_by` is `integration`, and its marker removed.
- Hidden entities keep working: Easy TRV reads and writes them as before; automations still see them.

## H. 0.5.1 changes

Owner decisions of 2026-10-15, after testing 0.5.0. They change A, B and the status sensor of the Phase 1 design; where this section and A–B differ, this section wins.

- **One sensor.** The status sensor (`ok` / `degraded` / `error`, `sensor.<room>_heating_status`) and the heating state sensor were doubled. The status sensor is removed; the heating state sensor stays, `unique_id` `<subentry_id>_state` and its entity id unchanged, and becomes a diagnostic entity (`EntityCategory.DIAGNOSTIC`, so A.1's "no entity category" no longer holds). At setup the integration removes the status sensors (`sensor` entities of the integration whose unique id ends with `_status`) from the entity registry, next to the 0.4.0 operating mode selects (`select`, `_operating_mode`). `RoomStatus` and the controller's `status` stay in the code; no entity shows them.
  - Automations on `sensor.<room>_heating_status` move to `sensor.<room>_heating_state`: `ok` is about `heating`, `frost` and the `off_*` states, `degraded` is `emergency` or a `restricted_*` state, `error` is `fault`.
- **Five restrictions instead of `restricted`.** `restricted` said too little. `HeatingState` has `restricted_unavailable`, `restricted_contact`, `restricted_unsupported`, `restricted_schedule` and `restricted_window_phase` in this order between `emergency` and `boost`, so there are fifteen states. `StateFacts.thermostat_restricted` becomes `thermostat_reasons`, the set of those of `unavailable`, `unsupported`, `schedule` and `window_phase` that hold for at least one thermostat, counting every reason of a thermostat (an `error` thermostat with the note `schedule` contributes `schedule`). `restricted_contact` holds while a window contact is silent (B). `thermostats` (A.3) still shows the first reason of a thermostat, for display only.
- **Hint.** The sensor gains the attribute `hint` (first of the attributes): plain text in the language of Home Assistant that names the affected thermostats and contacts, one phrase for each, for the reasons that hold in the order of `reasons`, joined by `; `; `None` when there is nothing to name and before the room has started. A thermostat is named by its device name (`labels.thermostat_name`), a contact by its state's name, else by its entity id.

  | Reason | Phrase (en) |
  |---|---|
  | `fault`, per thermostat in `error` | `{name}: error` |
  | `restricted_unavailable` | `{name} not reachable` |
  | `restricted_contact`, per silent contact | `{name} reports nothing ({why})`, `why`: `unavailable`, `unknown`, or `does not exist` (no state) |
  | `restricted_unsupported`, per thermostat | `{name}: lacks a function ({functions})` |
  | `restricted_schedule` | `{name} runs its own schedule` |
  | `restricted_window_phase` | `{name}: own window detection active` |

  `functions` are the plain-language names of the capabilities the thermostat lacks (`unsupported` without `not_in_profile`), labelled by intent with the labels the controller already has, else by the capability key; the controller exposes them as `unsupported_functions`. The phrases are the selector options `selector.hint.options.{fault,unavailable,contact,unsupported,schedule,window_phase,why_unavailable,why_unknown,why_missing}` with the placeholders `{name}`, `{why}` and `{functions}`. The sensor loads them in `async_added_to_hass`, before its first state write; until then, and for a phrase a translation lacks, the English phrase in the code applies.
- **Attributes**, in this order: `hint`, `reasons`, `since`, `window_off_at`, `thermostats`, `silent_contacts`, then what the status sensor showed: `active_sensor`, `source`, `setpoint_source`, `in_sync`, `last_error` (the attributes are always all present: `active_sensor`, `source` and `last_error` are `null` until the room has started and published them, so the set of keys never changes). The per-thermostat `trv_health`, `window_open`, `outdoor_cutoff` and `schedule_thermostats` of the status sensor are not carried over: `thermostats` and `reasons` say the same.
- **Icons** for the new states: `mdi:lan-disconnect`, `mdi:signal-off`, `mdi:puzzle-remove-outline`, `mdi:calendar-clock`, `mdi:window-open`.
