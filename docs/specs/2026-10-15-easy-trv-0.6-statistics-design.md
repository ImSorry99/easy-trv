# Easy TRV 0.6 — Statistics for later analysis

Derived from the owner's decisions of 2026-10-15 and the Phase 2 and 0.5 designs (`2026-10-14-easy-trv-phase2-design.md`, `2026-10-15-easy-trv-0.5-room-state-design.md`), which stay valid wherever this document is silent.

Goal (owner): start collecting data now for later evaluation and machine learning — control quality, Zigbee stability, windows, heating time. Only what Home Assistant does not record anyway.

## 1. What Home Assistant already records

The recorder keeps every state change of every entity, attributes included, for `purge_keep_days` (default 10; the owner raises it to 365). That covers room temperatures, humidity, the thermostats' target, mode and `hvac_action`, window contacts, the outdoor temperature and the room's heating state. Long-term statistics (5-minute and hourly mean/min/max, or sums for counters) are kept for ever, but only for sensors with a `state_class`.

So Easy TRV adds two kinds of sensors:

- **Data HA never sees:** writes and failed writes per thermostat. They happen inside Easy TRV.
- **Derived values as long-term statistics:** deviation, heating time, window openings and open time, thermostat dropouts. They could be recomputed from the raw history, but only while it is kept; as sensors with a `state_class` they survive for ever and are ready to chart.

The outdoor temperature gets nothing new: its sensor already has its own statistics.

## 2. Sensors

All are `entity_category: diagnostic` (owner: keep automatic dashboards clean), sit on the room device, and keep collecting whether or not anyone shows them. Counters and durations only ever grow (`state_class: total_increasing`) and continue after a restart (`RestoreSensor`); HA turns them into daily or weekly values itself (statistics card, utility meter helper).

### 2.1 Per room

| Key | Name de / en | Unit, class | Value |
|---|---|---|---|
| `deviation` | Regelabweichung / Control deviation | K, `measurement`, precision 1 | the active sensor's temperature minus the room setpoint, while the room heats (operating mode heat, no hold); `None` otherwise, so the statistics only cover heating time |
| `heating_time` | Heizzeit / Heating time | h, `duration`, `total_increasing`, precision 2 | time during which at least one thermostat of the room reports `hvac_action: heating`; unavailable when none of the room's thermostats has an `hvac_action` attribute |
| `window_openings` | Fensteröffnungen / Window openings | count, `total_increasing` | +1 each time the room's contacts go from all closed to any open (raw, before the open delay) |
| `window_open_time` | Fenster-offen-Zeit / Window open time | h, `duration`, `total_increasing`, precision 2 | time during which any contact of the room is open (raw) |

Rooms without window contacts get no window sensors. Silent contacts count as they resolve (spec 0.5 B: last state kept).

### 2.2 Per thermostat

| Key | Name de / en | Class | Value |
|---|---|---|---|
| `writes` | {thermostat} Schreibvorgänge / {thermostat} writes | `total_increasing` | +1 for every write request Easy TRV sends to the thermostat, retries included (read-backs do not count) |
| `write_failures` | {thermostat} Schreibfehler / {thermostat} failed writes | `total_increasing` | +1 for every write attempt whose outcome is `Failed` or `Mismatch` (not `Unsupported`, not a `Signal`) |
| `dropouts` | {thermostat} Ausfälle / {thermostat} dropouts | `total_increasing` | +1 each time the thermostat's climate entity goes from available to unavailable |

`{thermostat}` is the thermostat's device name (as in the 0.5.1 hint). Unique ids `<subentry_id>_<climate object id>_<key>`; suggested entity ids `sensor.<climate object id>_<key>`.

### 2.3 Not added (and why)

- Heating off time: total time minus heating time.
- Outdoor temperature: already a sensor with statistics.
- Thermostat downtime: the climate entity's `unavailable` periods are in the recorded history.
- Time within ±0.5 K: later, if the deviation statistics are not enough.

## 3. Updates

Durations are published on every transition and at least every 60 seconds while running, so the 5-minute statistics see them grow. The deviation is published when the sensor value or the setpoint changes. Counters are published at once.

## 4. Where the logic lives

- A small pure accumulator in `core/` (counts and running durations with start timestamps; no HA imports), tested on its own.
- The controller counts writes and failed writes where it executes operations, and dropouts where it already sees availability changes.
- `HoldInputs` reports the raw window state (any contact open, before the delay) to the accumulator.
- The heating time follows the thermostats' `hvac_action` attribute via a state listener.
- One sensor module (`statistics.py` or inside `sensor.py`, plan's choice) with `RestoreSensor` entities.

## 5. Translations, docs, release

- de and en for every name and unit-free label; README section "Statistics" (what is collected, how to chart it, the recorder tip `purge_keep_days`); `docs/testing-on-device.md` checks (heating time grows only while a TRV heats; one opening counts once; a failed write counts).
- Device check (spike): does the TRVZB report `hvac_action` in ZHA? If not, the heating time stays unavailable and the README says so.
- `CHANGELOG.md` section for 0.6.0.

## 6. Tests

- Accumulator: counts, durations across start/stop, restore of a stored value, no negative or decreasing values.
- Controller: a write counts once per attempt, a failed attempt counts once, Unsupported and Signal do not count, a dropout counts once per available→unavailable transition.
- Window: opening counted on the raw edge (not after the delay), repeated `on` reports do not count again, open time grows while open.
- Heating time: grows while any thermostat heats, stops when none heats, unavailable without `hvac_action`.
- Deviation: value while heating, `None` while off, held or on frost protection.
- Restore after restart continues the totals.

## 7. Out of scope

Pluggable control strategies and contributor profiles (owner's vision, own brainstorm after 0.6), InfluxDB (an HA integration, not Easy TRV's job), machine learning itself.
