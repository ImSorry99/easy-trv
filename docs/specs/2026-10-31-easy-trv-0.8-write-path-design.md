# Easy TRV 0.8 — A quieter, more robust write path

Derived from the owner's decisions of 2026-10-31 and the earlier designs, which stay valid wherever this document is silent.

Problem (owner): the Repairs notice "Thermostat … antwortet nicht" (`trv_unreachable`) appears again and again. Other integrations that feed the TRVZB an external temperature (Better Thermostat, ZHA's own entities) do not complain. A single Zigbee write that does not get through is normal.

## 1. Findings

Read in the installed zigpy 2.3.0 / zha 2.3.1, Better Thermostat (master, `model_fixes/TRVZB.py`) and our code.

1. **We cut zigpy short.** Every write and read runs under our own `asyncio.timeout(OPERATION_TIMEOUT)` of 20 s (`controller.py`). zigpy treats the TRVZB as an end device: it waits up to `APS_REPLY_TIMEOUT_EXTENDED` = 28 s for the answer and tries up to `DEFAULT_REQUEST_RETRIES` + 1 = 3 times, the later ones with a new route discovery (`zigpy/device.py: Device.request`). Our 20 s cancel the first try before zigpy gives up on it; its own retries never run. The request may still reach the thermostat and be applied while we count a failure and send it again.
2. **The read-back doubles the traffic and invents failures.** After every write we wait `verify_delay` (10 s) and read the attribute back. The thermostat already confirmed the write: zigpy returns its Write Attributes Response and we already reject anything but SUCCESS. ZHA's own entities trust exactly that (`write_attributes_safe`), Better Thermostat calls `number.set_value` and reads nothing back. A read that times out counts as a failed write although the write arrived.
3. **We report far too early.** Three attempts with 5 s and 15 s backoff: a thermostat that is out of reach for about two minutes gets an ERROR-severity Repairs issue, a log warning, the `easy_trv_write_failed` event and the heating state *fault*. The TRVZB keeps the external value for about two hours, so a missed write does no harm for a long time.
4. **Every start writes every setting blind.** `_apply_settings` sends window detection, adaptive mode, hysteresis and frost temperature to every thermostat at each start, and a start happens on every saved room or options change (the entry reloads). Each with a read-back: dozens of requests to sleepy devices at once, which is exactly what makes them time out.

## 2. Decisions

### A. Let zigpy do its job (timeout)

- `OPERATION_TIMEOUT` becomes a safety net only, well above zigpy's own worst case (3 × 28 s plus queueing at zigpy's concurrency limit): **180 s**. It stays so that a hung request cannot block a room's worker for ever.
- The same timeout applies to the remaining reads (B).
- Nothing else changes: zigpy's retries and route discovery happen inside one of our attempts.

### B. The thermostat's write response is the verification

A write is **verified** when the thermostat answers it with SUCCESS. What is read back afterwards is extra information, never a condition for the write to count as arrived.

- **No read-back** for a capability whose read-back can tell nothing the write response did not: no `signals`, no `also_read`, not `observe`. In the built-in profile that is `window_detection_flag`, `hysteresis`, `adaptive_mode` and `frost_protection`. The outcome is `Ok` right after the SUCCESS response, without waiting `verify_delay`.
- **Best-effort read-back** for the others (`external_temperature` with `also_read: [0x600E]`, `source_select` with its fail-safe signal, `setpoint` and `hvac_mode`, which are observed and carry the schedule signal). After `verify_delay` the value is read as today and judged as today (signal, accepted value, mismatch). Only the failure of the read itself changes: a read that times out or fails (`GatewayError`, `TimeoutError`) gives `Ok`, with a debug log line. A read that answers `UNSUPPORTED_ATTRIBUTE` is handled as today.
- The decision is derived from the profile, no new profile key: `needs_readback = observe or signals or also_read`.
- The **Read-back delay** setting stays; its description says it applies to the values that are read back (room temperature, source, target, mode).
- Statistics: `write_failures` counts failed writes and mismatches as before; a failed read-back no longer counts.
- Principle P4 of `REQUIREMENTS.md` reads: *Verified, not assumed. Every write is confirmed by the thermostat's answer; where a read-back tells more (fail-safe, schedule, a knob turned meanwhile), the value is read back as well. A write that does not arrive becomes visible.* B1 is updated to match.

### C. Report a thermostat only after its writes have failed for a while

The quick retry chain stays as it is (`max_attempts`, backoff 5 / 15 / 45 s), and so does what happens when it is used up internally: the capability is given up on, the thermostat goes into error, and everything that did not arrive is sent again once per refresh interval until it arrives. What changes is **when this becomes visible**.

- **Report delay: 60 minutes**, a constant (`RoomParams.report_after`, like `debounce` and `backoff`), no new setting. With the default refresh of 30 minutes it means: the chain failed, and the retry half an hour later failed too. The thermostat still has its external value for another hour.
- A thermostat counts as **failing since** the moment it first went into error (the same moment that starts the error-retry clock today). The time is kept in the thermostat's state (`failing_since`), not across restarts.
- **Before the report delay is over** (failing quietly): no Repairs issue, no log warning, no `easy_trv_write_failed` event. The give-up is a debug log line. The room's status, the heating state and its hint treat the thermostat as if it had no error (its baseline: ok, unavailable or unsupported). The retries run as described.
- **When the report delay is over** and the thermostat still owes something (the issue's capability, picked as today): the `trv_unreachable` issue is raised, now with severity **WARNING** instead of ERROR, one log warning, the `easy_trv_write_failed` event; from then on the room status is *error* and the heating state *fault*, as before. Checked on every tick (60 s).
- **When everything arrived**: if it had been reported, the issue clears, `easy_trv_recovered` fires and the info line "accepts writes again" is logged, as today. If it had not been reported, only a debug line; no event, no info. `failing_since` and the reported mark are cleared either way.
- The issue moving on to another capability that still fails (`_still_failing`) only says something (issue update, warning) once the thermostat has been reported.
- The issue text drops "auch nach {attempts} Versuchen" in favour of the time: "seit über {minutes} Minuten" / "for more than {minutes} minutes". The `attempts` placeholder goes away, `minutes` comes in.
- The **Attempts** setting keeps its meaning for the quick chain; its description no longer says "before the thermostat is reported as not responding" but "before Easy TRV switches to retrying once per refresh interval".
- Window, firmware and the other issues are not touched.

### D. Settings are written only when the thermostat has another value

- Before a **setting** is written (`SETTING_INTENTS`: window detection, adaptive mode, hysteresis, frost temperature), the controller looks at the value zigpy last knew for the attribute (its attribute cache, filled by reports, reads and our own successful writes, and kept in ZHA's database across restarts). If that value is one the write would accept (`op.accept`), nothing is sent and the outcome is `Ok`. It does not count as a write in the statistics.
- If the cache has no value, or another one, the setting is written as today.
- The gateway gains `cached(ieee, endpoint, cluster, attribute) -> int | None` via the zigpy cluster's `get(attribute)`, which reads only the cache; any failure of the internal API reads as `None` (write as today).
- Only settings. The source, the room temperature, setpoint and mode are always written: the source and value because the thermostat may have fallen back without anyone knowing, setpoint and mode because the room's echo detection relies on its own writes.
- A stale cache that matches can skip a write that was needed (a setting changed at the thermostat without a report). That is accepted: ZHA's own entities show the same stale value, and changing a setting in Easy TRV writes it.

## 3. Out of scope

- No change to the refresh interval, the minimum change, debouncing or the error-retry cadence.
- No subscription to 0x600E reports instead of the read-back; whether the TRVZB reports it is unverified.
- No new settings.

## 4. Testing

- Gateway: `cached` returns the cached value, `None` when absent or when the API fails.
- Controller: a setting capability is written without a read; a readback capability whose read fails gives `Ok`; a read that answers with a signal or another value still gives `Signal` / `Mismatch`; a cached setting that matches is not written and not counted; one that differs is written; `OPERATION_TIMEOUT` is 180 s.
- Room logic: a give-up raises nothing visible (no issue, no warning, no event, status and heating state unchanged); a tick before 60 minutes raises nothing; a tick at or after 60 minutes raises the issue once with `minutes`, warns once, fires the event, and status and heating state show the error; recovery before the report is silent; recovery after it clears the issue and fires `recovered`; `_still_failing` stays silent before the report.
- Issues: `trv_unreachable` has severity WARNING and the `minutes` placeholder in both languages.
- Existing tests that expect the issue right after the attempts are adjusted to the new timing.
