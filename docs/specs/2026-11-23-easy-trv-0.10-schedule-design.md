# Easy TRV 0.10 — Schedules from a Home Assistant `schedule` helper

Derived from the owner's decisions of 2026-11-23 (concept "Zeitpläne per schedule-Helfer", accepted as proposed) and the earlier designs, above all `2026-10-18-easy-trv-0.7-presence-design.md`, which stays valid wherever this document is silent.

Goal (owner): rooms heat when they are used. Rooms can run opposite to each other (the living room in the day, the bedroom from the evening). It must stay simple to handle.

Use case behind it: the bedroom is lowered during the day and warm at bedtime (22:00–23:00); it starts heating at 21:00 so it is warm in time.

Not in this step: a house-wide schedule, a learned preheat time, a schedule action other than setback (frost or off), the thermostat's own weekly schedule (`auto`), which Easy TRV keeps leaving alone.

## 1. Behaviour

- A room may have a **schedule entity** (domain `schedule`). Without one nothing changes.
- **Schedule on:** the room heats to its wish. When the active block carries the data key `temperature`, that value becomes the room's wish when the block starts (or its `temperature` changes), as if someone had set it; `setpoint_source` is `schedule`. A value outside the setpoint range is clamped; a value that is not a number is ignored (warning in the log). A block without `temperature` leaves the wish alone.
- **Schedule off:** the room is **lowered** by the schedule setback (default 3 K), never below the frost protection temperature (a wish below it stays), exactly like the away setback.
- **A target set while the schedule is off** (Home Assistant or a knob) is an override: the room heats to it until the schedule turns on again. A target set while it is on lasts until the next block that carries a `temperature`.
- **Away and schedule off together** do not stack: the larger setback applies. Away with action *off* is a hold as before and wins.
- The schedule acts only while the room **heats** (operating mode heat). Frost protection and off are the user's choice and win. A block temperature that arrives during frost protection becomes the setpoint frost returns to; one that arrives while the room is off becomes its wish for when it is switched on.
- Window, outdoor cut-off: unchanged; when the hold ends the room returns to what the schedule says now.
- A schedule entity that is `unavailable`, `unknown` or missing reads as **on** (the room heats normally), so a broken helper never leaves a room cold.
- **Start:** the schedule is read from its state. A remembered override is restored and dropped if the schedule reads on.

## 2. Settings

| Key | Where | Values | Default |
|---|---|---|---|
| `schedule_entity` | room, first step (with thermostats, sensors, contacts) | a `schedule` entity, optional | none |
| `schedule_setback_kelvin` | options, new section **Schedule**; room override in the room settings | 0.5–15 K | 3 |

The upper bound is 15 K so that a room can be brought down to frost protection (the setback never goes below it). Any change of these keys reloads the integration, as other settings do.

## 3. Entities

- Room thermostat attributes: `schedule_entity` (absent without), `schedule` (`on` / `off`), `schedule_override` (bool).
- Heating state: new `setback_schedule` ("Abgesenkt: Zeitplan" / "Lowered: schedule") after `setback_away`. Hint: `Schedule {name} is off` naming the helper. The card shows it in the lowered group.
- Restore data of the room thermostat gains `schedule_override`.

## 4. Core design

- `RoomConfig.schedule_setback: float | None` (`None` = no schedule).
- `RoomState.schedule_off`, `RoomState.schedule_override`, `RoomState.schedule_temperature` (the block temperature last applied, so the same block does not set the wish again).
- Event `ScheduleChanged(on: bool, temperature: float | None)`; `Start` gains `schedule_on` and `schedule_temperature`; `RestoreRoom` gains `schedule_override`.
- `setpoint.schedule_acts()` mirrors `away_acts()`; `lowered()` is true when either acts; `target()` takes the larger of the acting setbacks.
- `hold.on_schedule()` mirrors `hold.on_presence()`: the state changes, the new target is written when it differs.
- A target set from Home Assistant or a knob while the schedule acts sets `schedule_override`.

## 5. Home Assistant side

- `ScheduleInput` (in `observation.py`) tracks the entity, reads on/off and `temperature`, feeds `ScheduleChanged` only on a change of either.
- The controller exposes `schedule_entity`, `schedule_on`, `schedule_override` for the thermostat entity and the sensor.
- Diagnostics: per room the schedule entity, on/off, override.

## 6. Tests

Core: on/off lowers and restores, block temperature sets the wish once, override in both directions, away and schedule together, frost and off, window hold, restore. HA side: input (on, off, temperature, unavailable, not a number), settings and flow, attributes, heating state and hint, translations.
